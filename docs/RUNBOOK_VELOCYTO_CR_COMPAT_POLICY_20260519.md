# RUNBOOK: Count-Preserving Velocyto CR-Compat Policy

Date: 2026-05-19

Status: design runbook for the future count-preserving `CRCompat` policy. The
native Velocyto MEX writer for the current legacy STAR Velocyto policy is
implemented and is the production packaging path today; `CRCompat` remains a
planned compatibility policy until the tests below pass.

Current production note:

- New UCSF/MSK/JAX production runs should not call `prepare_velocyto_mex.py`.
  STAR writes `outs/raw_velocyto_feature_bc_matrix` and
  `outs/filtered_velocyto_feature_bc_matrix` internally through
  `VelocytoMexWriter`.
- OCM production splits per-sample Velocyto MEX natively and maps GeneFull
  columns to Velocyto columns by normalized barcode key, not by position.
- The current delivered velocity layers follow legacy STAR Velocyto semantics.
  They are not guaranteed to sum exactly to `GeneFull` until `CRCompat` is
  implemented and selected explicitly.

## Goal

Add a STAR-suite Velocyto compatibility policy whose delivered Velocyto total
counts are identical to the CR-compatible `GeneFull` count matrix.

The production invariant is:

```text
VelocytoCR matrix.mtx == GeneFull matrix.mtx
VelocytoCR spliced + unspliced + ambiguous == GeneFull matrix.mtx
```

This invariant must hold on both raw and filtered barcode axes. The motivation is
delivery clarity: downstream `h5ad` / `h5mu` users should not see one total count
surface in `X` and a different total count surface when summing RNA velocity
layers.

## Scope

Keep the existing STAR Velocyto policy available and unchanged. Add a separate
compatibility policy for production outputs:

- existing behavior: `Velocyto` / legacy STAR Velocyto semantics
- new behavior: `VelocytoCR` / GeneFull-count-preserving CR-compatible semantics

The compatibility mode should reuse the current STAR Velocyto process. Do not
add an external post hoc counter and do not add a new per-read sidecar unless a
test proves the existing stream is insufficient.

## Existing Machinery

The current Velocyto path already has the correct shape for this work:

- per-read transcript/mask records are generated by
  `Transcriptome::classifyAlign`
- records are written in the existing `SoloReadFeature_record_*` Velocyto path
- Velocyto counting groups records by corrected `(CB, UMI)`
- the grouping reads CB/UMI/status from the gene-like feature read-info source
- `recordReadInfo` is populated during GeneFull collapse and already carries the
  corrected CB, corrected UMI, and accepted/drop status
- `--soloCrMultimapRescue yes` can reduce `nTr` to a single rescued alignment
  before Velocyto annotation

Important existing locations:

- `core/legacy/source/ReadAlign_outputAlignments.cpp`
  - CR multimap rescue mutates `trMult` / `nTr` before classification.
- `core/legacy/source/Transcriptome_classifyAlign.cpp`
  - current Velocyto transcript/mask annotation.
- `core/legacy/source/SoloFeature_collapseUMIall.cpp`
  - GeneFull `MultiGeneUMI_CR` and `recordReadInfo` status assignment.
- `core/legacy/source/SoloFeature_countVelocytoBridge.cpp`
  - Velocyto grouping and finalization.
- `core/legacy/source/VelocytoMexWriter.cpp`
  - native MEX packaging; should be extended to package CR-compatible outputs.
- `core/legacy/source/OcmMultiMaterialize.cpp`
  - OCM pooled-to-per-sample MEX materialization; must preserve the same
    GeneFull/VelocytoCR count invariant for each emitted sample.

## Non-Goals

- Do not replace external `velocyto.py`.
- Do not mutate the validated legacy STAR Velocyto path by default.
- Do not redefine `GeneFull` counting.
- Do not accept a compatibility output where `spliced + unspliced + ambiguous`
  differs from `GeneFull`.

## CLI Contract

Add a policy parameter rather than overloading the feature name:

```text
--soloVelocytoPolicy Legacy|CRCompat|Both
```

Recommended defaults:

- default: `Legacy`
- production UCSF/MSK/JAX wrappers: `CRCompat` after validation
- development/parity runs: `Both`

`CRCompat` requires:

- `--soloFeatures GeneFull Velocyto`
- `--soloCrGexFeature genefull`
- `--soloUMIfiltering MultiGeneUMI_CR`
- `--soloUMIdedup 1MM_CR`
- `--soloCellFilter EmptyDrops_CR` for production-compatible filtered outputs

The parameter parser should reject `CRCompat` if no `GeneFull` feature is
requested, because the compatibility policy needs a GeneFull matrix as the
authoritative total count surface.

## Output Contract

Legacy outputs remain unchanged:

```text
Solo.out/Velocyto/
outs/raw_velocyto_feature_bc_matrix/
outs/filtered_velocyto_feature_bc_matrix/
```

CR-compatible outputs use explicit names during validation:

```text
Solo.out/VelocytoCR/
outs/raw_velocyto_cr_feature_bc_matrix/
outs/filtered_velocyto_cr_feature_bc_matrix/
outs/velocyto_cr_feature_bc_matrix_manifest.json
```

Once the CR-compatible policy is validated, downstream production wrappers may
map the CR-compatible directories into the h5ad velocity layers by default. Do
not silently swap legacy and CR-compatible directory meanings in tests.

The CR-compatible MEX directories must contain:

```text
features.tsv(.gz)
barcodes.tsv(.gz)
matrix.mtx(.gz)
spliced.mtx(.gz)
unspliced.mtx(.gz)
ambiguous.mtx(.gz)
```

For every directory:

- `features.tsv` must match the corresponding GeneFull features.
- `barcodes.tsv` must match the corresponding GeneFull barcodes.
- `matrix.mtx` must be byte/logical equivalent to the corresponding GeneFull
  matrix.
- `spliced + unspliced + ambiguous` must equal `matrix.mtx`.

## Policy Definition

`GeneFull` is authoritative for molecule admission and total counts.

VelocytoCR is only a partition of accepted GeneFull counts:

1. If Velocyto evidence classifies an accepted molecule as spliced, add it to
   `spliced`.
2. If Velocyto evidence classifies an accepted molecule as unspliced, add it to
   `unspliced`.
3. If evidence is mixed, contradictory, absent, or cannot be restricted cleanly
   to the accepted GeneFull count surface, add it to `ambiguous`.

The compatibility layer must never drop a GeneFull count. Ambiguous is the
absorbing class for unclassifiable accepted molecules.

## Implementation Plan

### Phase 1. Parameter and routing

Add a `soloVelocytoPolicy` parameter in `ParametersSolo`:

- enum/string values: `Legacy`, `CRCompat`, `Both`
- code default: `Legacy`
- CR bundle / production wrapper opt-in: `CRCompat`

Routing:

- `Legacy`: current `Solo.out/Velocyto` path only
- `CRCompat`: current Velocyto stream plus GeneFull reconciliation into
  `Solo.out/VelocytoCR`
- `Both`: emit both surfaces for parity and debugging

### Phase 2. Reuse existing Velocyto molecule process

Keep the current Velocyto record generation and grouping:

- keep `trVelocytoType` generation
- keep `(CB, corrected UMI)` grouping via GeneFull read-info
- keep the existing spliced/unspliced/ambiguous classifier as the first-pass
  classification signal

Do not introduce a second read stream. The existing process is the internal
molecule evidence.

### Phase 3. Count-preserving reconciliation

After first-pass Velocyto classification, reconcile against the authoritative
GeneFull matrix on the same axis.

For each `(cell, gene)`:

```text
gene_full = GeneFull[cell, gene]
velo_sum = spliced[cell, gene] + unspliced[cell, gene] + ambiguous[cell, gene]
```

Rules:

- if `velo_sum == gene_full`: keep the layer values
- if `velo_sum < gene_full`: add `gene_full - velo_sum` to `ambiguous`
- if `velo_sum > gene_full`: fail the run in CRCompat mode

The surplus case should be fatal during implementation because it means the
Velocyto first-pass policy counted molecules outside the GeneFull count surface.
Do not hide this by subtracting from arbitrary layers. If this occurs on real
data, fix the policy restriction in the Velocyto finalizer before enabling
production.

This phase produces an exact total-count invariant without inventing a new
sidecar.

### Phase 4. Native MEX writer support

Extend `VelocytoMexWriter` to package either legacy or CR-compatible directories:

- source `Solo.out/Velocyto` -> existing `outs/*_velocyto_feature_bc_matrix`
- source `Solo.out/VelocytoCR` -> new `outs/*_velocyto_cr_feature_bc_matrix`

Manifest additions:

```json
{
  "velocyto_policy": "CRCompat",
  "gene_expression_feature": "GeneFull",
  "count_preserving": true,
  "deficit_filled_to_ambiguous": 12345,
  "surplus_cells_genes": 0
}
```

### Phase 5. Downstream h5ad / h5mu integration

Update downstream builders to choose the policy explicitly:

- `scripts/build_gene_full_velocyto_h5ad.py`
  - add `--velocyto-policy legacy|crcompat`
  - `crcompat` reads `outs/raw_velocyto_cr_feature_bc_matrix`
  - assert `X == spliced + unspliced + ambiguous`
  - write `adata.uns["velocyto_policy"] = "CRCompat"`
- `scripts/build_multiome_mudata.py`
  - preserve and verify RNA layer invariant when `--require-rna-velocity-layers`
    is used
  - write MuData-level provenance for Velocyto policy

### Phase 6. OCM per-sample MEX materialization

The OCM materializer must use the same policy and invariant as the run-level
writer. This is required because OCM splits a pooled run into per-sample MEX
surfaces, and downstream users will consume those per-sample surfaces as if they
were normal STAR/CellRanger-style sample outputs.

Extend `OcmMultiMaterialize` so that when `soloVelocytoPolicy` is `CRCompat` or
`Both`:

- it reads the run-level `Solo.out/VelocytoCR` or equivalent reconciled
  `VelocytoCR` data
- it subsets `raw_velocyto_cr_feature_bc_matrix` with the same raw barcode
  columns used for the per-sample GeneFull raw MEX
- it subsets `filtered_velocyto_cr_feature_bc_matrix` with the same filtered
  barcode columns used for the per-sample GeneFull filtered MEX
- it writes per-sample CR-compatible velocity outputs under:

```text
samples/<sample>/run/outs/raw_velocyto_cr_feature_bc_matrix/
samples/<sample>/run/outs/filtered_velocyto_cr_feature_bc_matrix/
```

For each sample and each split (`raw`, `filtered`):

```text
sample GeneFull matrix.mtx
  == sample VelocytoCR matrix.mtx
  == sample spliced + sample unspliced + sample ambiguous
```

This check should run inside the materializer or immediately after it. A failure
is fatal in `CRCompat` mode because it means OCM split logic drifted from the
run-level GeneFull/VelocytoCR relationship.

## Test Plan

### Unit Test 1. Reconciliation math

Create a tiny in-memory matrix fixture:

- GeneFull has counts for three genes and two barcodes.
- Velocyto first pass has one exact match.
- Velocyto first pass has one deficit.
- Velocyto first pass has one surplus.

Expected:

- exact match passes unchanged
- deficit is added to ambiguous
- surplus returns failure


## Acceptance Criteria

Implementation is acceptable when:

- default legacy Velocyto outputs are unchanged
- CR-compatible raw and filtered Velocyto total matrices exactly equal GeneFull
- CR-compatible layer sums exactly equal the total matrices
- OCM per-sample GeneFull and VelocytoCR MEX totals exactly match for raw and
  filtered outputs
- surplus reconciliation is zero on UCSF/MSK/JAX smoke tests
- downstream h5ad and h5mu builders record `velocyto_policy = CRCompat`
- production runbooks explicitly opt into CR-compatible Velocyto for delivered
  RNA velocity layers

## Rollout Plan

1. Implement parameter parsing and no-op routing.
2. Implement CR-compatible reconciliation on existing Velocyto first-pass output.
3. Add unit tests for reconciliation and legacy default behavior.
4. Add tiny smoke.
5. Run UCSF/OCM downsample smoke with `Both`.
6. Update downstream h5ad/h5mu builders.
7. Switch JAX/MSK/UCSF production wrappers to `CRCompat` after smoke gates pass.

## Open Questions

- Should production wrappers emit legacy and CR-compatible surfaces for one
  transition run, or only CR-compatible after validation?
- Should `CRCompat` fail if deficit fill exceeds a configured fraction? The
  total invariant remains valid, but a large ambiguous fill would indicate poor
  velocity evidence.
- Should the final delivered directory keep the historical
  `raw_velocyto_feature_bc_matrix` name after validation, or should it remain
  explicit as `raw_velocyto_cr_feature_bc_matrix`?
